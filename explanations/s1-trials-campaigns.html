Tập 3 · Code

Service quyết định lấy gì

src/trials/trials.service.tsTypeScript
@Injectable()
export class TrialsService {
  constructor(private readonly prisma: PrismaService) {}

  // Chỉ trả campaign đang bật; campaign tắt không nên xuất hiện cho user.
  listActiveCampaigns(): Promise<CampaignView[]> {
    return this.prisma.trialCampaign.findMany({
      where: { active: true },
      select: {
        campaignId: true,
        name: true,
        durationDays: true,
        active: true,
      },
      orderBy: { campaignId: 'asc' },
    });
  }
}

Vì sao lọc active: true?

Campaign có thể bị tắt mà không xóa — ví dụ hết chương trình khuyến mãi. Lọc ở query đảm bảo user không thấy campaign đã đóng, và không cần xử lý ở frontend.

Vì sao chỉ select 4 cột?

Bảng hiện chỉ có 4 cột, nhưng thói quen tốt là chỉ lấy thứ sẽ trả về. Sau này thêm cột nội bộ (ngân sách, ghi chú...) sẽ không vô tình lộ ra API.

Vì sao sắp xếp theo campaignId?

Kết quả ổn định giữa các lần gọi. Nếu không sắp xếp, thứ tự do database quyết định và có thể thay đổi — frontend sẽ thấy danh sách nhảy loạn.

Tập 4 · Controller

Guard đứng trước, service đứng sau

src/trials/trials.controller.tsTypeScript
@Controller('api/trials')
export class TrialsController {
  constructor(private readonly trialsService: TrialsService) {}

  @Get('campaigns')
  @UseGuards(JwtAuthGuard)
  listCampaigns(): Promise<CampaignView[]> {
    return this.trialsService.listActiveCampaigns();
  }
}
Route này không cần biết user là ai

Nó chỉ cần biết request có token hợp lệ. Vì vậy không dùng @CurrentUser() — thêm vào chỉ làm code rối. Khi làm claim mới cần userId để biết ai đang nhận trial.

Phần thưởng · Hỏi đáp

Câu hỏi có thể bị hỏi

Vì sao trả mảng trực tiếp mà không bọc trong object?

Endpoint chỉ trả một loại dữ liệu, không cần metadata. Mảng trực tiếp đơn giản cho frontend. Nếu sau này cần phân trang hoặc tổng số, có thể đổi thành { items, total } — đó là thay đổi API có kiểm soát.

Ai được gọi route này?

Mọi tài khoản có token hợp lệ, cả USER và ADMIN. Chưa có phân quyền theo role. Nếu cần giới hạn, thêm role guard — ví dụ chỉ ADMIN được xem campaign nháp.

Campaign bị tắt giữa lúc user đang xem thì sao?

Lần gọi tiếp theo sẽ không thấy campaign đó. Nếu user đã mở form claim trước khi campaign bị tắt, bước POST /claims sẽ kiểm tra lại và trả 422 CAMPAIGN_INACTIVE — không tin dữ liệu cũ từ client.

Vì sao không cache danh sách campaign?

Danh sách rất nhỏ và ít thay đổi, nhưng cache thêm phức tạp: phải biết khi nào xóa cache. Với MVP, query trực tiếp đủ nhanh. Khi có hàng nghìn request/phút mới cân nhắc.

Nếu database không có campaign nào thì sao?

Trả 200 []. Đây không phải lỗi — hệ thống vẫn hoạt động, chỉ là chưa có chương trình nào đang bật.

Tập tiếp theo

POST /api/trials/claims

Đây là phần khó nhất của S1: tạo claim với idempotency, ghi outbox trong cùng transaction, gọi S2 và áp auto policy.

Đề xuất chia nhỏ: (1) tạo claim PENDING_RISK_CHECK + outbox, (2) gọi S2, (3) áp kết quả ALLOW / VERIFY / REJECT. Mỗi bước test xong mới sang bước sau.
