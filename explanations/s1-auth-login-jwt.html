Đăng nhập & cấp JWT

Kiểm tra mật khẩu bằng bcrypt, ký token bằng HMAC-SHA256, trả về accessToken để client dùng cho các request sau.

200 OK 401 INVALID_CREDENTIALS @nestjs/jwt bcrypt chưa có guard
Tóm tắt

Thêm POST /api/auth/login: tìm tài khoản theo email đã chuẩn hóa, so sánh mật khẩu bằng bcrypt.compare, rồi ký JWT chứa sub (userId) và role. Sai email hoặc sai mật khẩu đều trả cùng một lỗi 401 để tránh dò email tồn tại. Token sống 1 giờ.

JWT là gì?

JWT (JSON Web Token) giống một tấm vé có chữ ký. Server phát vé sau khi kiểm tra mật khẩu đúng. Vé ghi bạn là ai và có quyền gì; chữ ký đảm bảo không ai sửa được nội dung.

header

Thuật toán

Ví dụ {"alg":"HS256","typ":"JWT"} — cho biết token được ký bằng HMAC-SHA256.

payload

Dữ liệu

Chứa sub, role, iat, exp. Ai cũng đọc được, nên không đặt mật khẩu hay dữ liệu nhạy cảm.

signature

Chữ ký

HMAC của header + payload với JWT_SECRET. Sửa payload là chữ ký sai, server từ chối.

Hiểu nhầm thường gặp

JWT không mã hóa nội dung, chỉ ký. Bất kỳ ai có token đều decode được payload. Vì vậy tuyệt đối không đặt mật khẩu, số CCCD hay secret vào payload.

Một lần đăng nhập đi qua đâu?

  • 1. Client gửi email + password POST /api/auth/login qua NGINX :8080
  • 2. ValidationPipe kiểm tra LoginDto email đúng định dạng, password không rỗng, tối đa 72 ký tự
  • 3. AuthService chuẩn hóa email trim().toLowerCase() để khớp với dữ liệu lúc đăng ký
  • 4. Prisma tìm tài khoản findUnique({ where: { emailNormalized } }), chỉ lấy userId, passwordHash, role
  • 5. bcrypt.compare kiểm tra mật khẩu sai hoặc không có tài khoản → 401 INVALID_CREDENTIALS
  • 6. Ký JWT và trả về signAsync({ sub, role }) → 200 + accessToken, tokenType, expiresIn

DTO — chỉ cần đúng hình dạng

export class LoginDto {
  @IsEmail({}, { message: 'Email không hợp lệ' })
  @MaxLength(254, { message: 'Email quá dài' })
  email!: string;

  // Login không áp policy mạnh như register: chỉ cần khớp mật khẩu đã lưu.
  @IsString()
  @MinLength(1, { message: 'Mật khẩu không được để trống' })
  @MaxLength(72, { message: 'Mật khẩu không được quá 72 ký tự' })
  password!: string;
}

Service — nơi quyết định đúng/sai

src/auth/auth.service.tsTypeScript
async login(dto: LoginDto): Promise<LoginResult> {
  const emailNormalized = dto.email.trim().toLowerCase();

  const account = await this.prisma.account.findUnique({
    where: { emailNormalized },
    select: { userId: true, passwordHash: true, role: true },
  });

  const passwordMatches = account
    ? await compare(dto.password, account.passwordHash)
    : false;

  // Cùng một thông báo cho "email không tồn tại" và "sai mật khẩu":
  // tránh để kẻ tấn công dò xem email nào đã đăng ký.
  if (!account || !passwordMatches) {
    throw new UnauthorizedException({
      code: 'INVALID_CREDENTIALS',
      message: 'Email hoặc mật khẩu không đúng',
    });
  }

  const accessToken = await this.jwtService.signAsync({
    sub: account.userId,
    role: account.role,
  });

  return {
    accessToken,
    tokenType: 'Bearer',
    expiresIn: JWT_EXPIRES_IN_SECONDS,
  };
}
Vì sao chỉ lấy 3 cột?

select giới hạn dữ liệu trả về từ DB. Không lấy emailNormalized hay các cột thừa giúp giảm nguy cơ vô tình trả nhầm dữ liệu ra response và giảm tải I/O.

Module — cấu hình JWT một lần

src/auth/auth.module.tsTypeScript
JwtModule.registerAsync({
  useFactory: () => {
    const secret = process.env.JWT_SECRET;

    if (!secret) {
      // Fail fast khi khởi động thay vì để login lỗi mơ hồ lúc chạy.
      throw new Error('JWT_SECRET chưa được cấu hình');
    }

    return {
      secret,
      signOptions: { expiresIn: JWT_EXPIRES_IN_SECONDS },
    };
  },
}),

Câu hỏi có thể bị hỏi

JWT khác session cookie thế nào?

Session lưu trạng thái ở server: mỗi request phải tra DB/Redis. JWT không lưu trạng thái: server chỉ kiểm tra chữ ký. Đổi lại, JWT khó thu hồi ngay và dung lượng lớn hơn cookie session.

Vì sao dùng sub mà không phải userId?

sub là claim chuẩn trong JWT (RFC 7519), nghĩa là “subject”. Dùng tên chuẩn giúp thư viện và hệ thống khác hiểu token mà không cần tài liệu riêng. role là claim tự đặt, được phép.

Ai đó sửa role trong token để thành ADMIN được không?

Không. Sửa payload làm chữ ký không còn khớp. Server verify bằng JWT_SECRET và từ chối token. Điều kiện là secret không bị lộ.

Nếu JWT_SECRET bị lộ thì sao?

Kẻ tấn công ký được token giả với bất kỳ role nào. Khi đó phải đổi secret, khiến toàn bộ token cũ mất hiệu lực, và rà soát log. Vì vậy secret phải nằm trong env, không commit, không log.

Vì sao bcrypt.compare chậm mà vẫn dùng?

Chậm là mục đích. Kẻ tấn công có hash cũng phải thử từng mật khẩu với cost 12, rất tốn thời gian. Người dùng thật chỉ chịu ~300ms mỗi lần đăng nhập.

Token nên lưu ở đâu phía client?

Chưa làm frontend. Khi làm, cần cân nhắc: localStorage dễ dùng nhưng dễ bị XSS đọc; cookie HttpOnly an toàn hơn với XSS nhưng cần chống CSRF. Với đồ án, có thể dùng localStorage và ghi rõ giới hạn.

Bước tiếp theo

JwtAuthGuard + GET /api/users/me.

Guard đọc header Authorization: Bearer <token>, verify chữ ký, gắn user vào request. Route /me trả thông tin tài khoản hiện tại. Test: không token → 401, token hợp lệ → 200.
