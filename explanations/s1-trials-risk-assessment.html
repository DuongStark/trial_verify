Vì sao không đi qua gateway?

Route /internal/ là giao tiếp nội bộ, không dành cho client. NGINX chặn mọi request /internal/ từ bên ngoài. S1 gọi thẳng http://graph-risk:3002 trong mạng Docker.

Vì sao gọi HTTP mà không dùng RabbitMQ?

Vì claim flow cần câu trả lời ngay trong request để biết claim đang chờ, được duyệt hay bị từ chối.

HTTP đồng bộ S1 hỏi → S2 trả lời ngay → S1 tiếp tục xử lý
⇄
RabbitMQ bất đồng bộ S1 gửi event → không chờ → consumer xử lý sau
Tiêu chíHTTP đồng bộRabbitMQ bất đồng bộ
Có kết quả ngay? Có, trong cùng request Không, phải chờ consumer và nhận kết quả qua message khác
Độ phức tạp Thấp: gọi, đọc response, xử lý lỗi Cao: correlationId, queue kết quả, retry, DLQ
Coupling S1 cần S2 đang sống tại thời điểm gọi S1 không cần S2 sống, message nằm trong queue
Độ trễ Thấp (vài chục ms nội bộ) Cao hơn, phụ thuộc consumer
Phù hợp Quyết định real-time, cần phản hồi ngay Event, audit, fan-out, xử lý nền
Trong dự án S1 gọi S2 chấm điểm Outbox → S3, cập nhật graph, audit

Nếu dùng RabbitMQ cho S1 → S2 thì sao?

  1. S1 publish message “hãy chấm claim này”. Không có kết quả ngay.
  2. S2 consume, chấm điểm, rồi publish kết quả vào một queue khác.
  3. S1 phải consume queue kết quả, dùng correlationId để biết kết quả thuộc claim nào.
  4. Client muốn biết kết quả phải poll GET /claims/{id}.

Luồng này hợp lý khi chấp nhận xử lý nền, nhưng với claim trial ta muốn biết ngay để trả 201/202 và áp policy. Dùng HTTP đơn giản hơn nhiều.

Vậy RabbitMQ dùng ở đâu?

Thiết kế v4 chốt: REST/HTTP cho giao tiếp đồng bộ, RabbitMQ cho event bất đồng bộ. RabbitMQ nằm sau outbox:

Luồng eventtext
S1 tạo claim ──► s1_outbox (cùng transaction)
                    │
                    ▼
              Outbox publisher (worker)
                    │
                    ▼
                 RabbitMQ
                /        \
               ▼          ▼
        S3 tạo case   S2 cập nhật graph/audit
Điểm mấu chốt

Quyết định “cho hay không cho trial” cần đồng bộ. Việc “ghi audit, tạo case, cập nhật graph” không cần chặn response, nên đẩy qua RabbitMQ. Hai loại giao tiếp giải hai bài toán khác nhau, không thay thế nhau.

Nếu S2 chết thì sao?

HTTP sẽ lỗi/timeout. S1 không làm sập cả request: claim đã lưu, giữ PENDING_RISK_CHECK, ghi lastError và hẹn retry. Đây là cách giữ tính đúng đắn dù giao tiếp đồng bộ. Worker retry sẽ thử lại sau.

Phía S1

RiskClient: gọi HTTP có timeout

src/trials/risk-client.service.tsTypeScript
async assess(input: RiskAssessmentInput): Promise<RiskAssessmentResponse> {
  const baseUrl = process.env.RISK_SERVICE_URL ?? 'http://graph-risk:3002';
  const token = process.env.INTERNAL_SERVICE_TOKEN;
  const timeoutMs = Number(process.env.RISK_HTTP_TIMEOUT_MS ?? 2000);

  if (!token) {
    throw new Error('INTERNAL_SERVICE_TOKEN chưa được cấu hình');
  }

  const response = await fetch(
    `${baseUrl}/internal/risk/assessments`,
    {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'X-Internal-Token': token,
      },
      body: JSON.stringify(input),
      signal: AbortSignal.timeout(timeoutMs),
    },
  );

  if (!response.ok) {
    throw new Error(`S2 trả HTTP ${response.status}`);
  }

  return (await response.json()) as RiskAssessmentResponse;
}

Vì sao dùng fetch thay vì axios?

Node 24 có fetch sẵn. Không cần thêm dependency, không cần cấu hình module. AbortSignal.timeout(2000) đảm bảo S1 không treo nếu S2 chậm — sau 2 giây request bị huỷ.

Lưu assessment vào claim

src/trials/trials.service.tsTypeScript
private async assessClaim(claim: ClaimView, userId: string) {
  // Retry sau khi S2 đã thành công → không gọi lại.
  if (claim.assessmentId) {
    return claim;
  }

  try {
    const assessment = await this.riskClient.assess({
      claimId: claim.claimId,
      userId,
      campaignId: claim.campaignId,
      evaluationVersion: claim.evaluationVersion,
    });

    // Bước 3b chỉ lưu kết quả; chưa đổi status.
    return await this.prisma.trialClaim.update({
      where: { claimId: claim.claimId },
      data: {
        assessmentId: assessment.assessmentId,
        riskScore: assessment.score,
        riskLevel: assessment.level,
        decision: assessment.decision,
        reasonsJson: assessment.reasons,
      },
      select: CLAIM_SELECT,
    });
  } catch (error) {
    // S2 lỗi: giữ PENDING để retry sau.
    await this.prisma.trialClaim.update({
      where: { claimId: claim.claimId },
      data: {
        lastError: error instanceof Error ? error.message : 'S2 không phản hồi',
        retryCount: { increment: 1 },
        nextRetryAt: new Date(Date.now() + 30_000),
      },
    }).catch(() => undefined);

    return claim;
  }
}
Vì sao không trả lỗi 500 khi S2 chết?

Claim đã được tạo và lưu. Nếu trả 500, client tưởng chưa có claim và có thể thử campaign khác. Giữ 202 + PENDING_RISK_CHECK phản ánh đúng: yêu cầu đã nhận, đang chờ xử lý. Worker retry (sau này) sẽ gọi lại S2.

Endpoint tối thiểu

src/risk/risk.service.tsTypeScript
assess(dto: CreateAssessmentDto): AssessmentResult {
  const assessmentKey = `${dto.claimId}:${dto.evaluationVersion}`;

  // Cùng claim + cùng version → cùng assessmentId.
  const assessmentId = createHash('sha256')
    .update(assessmentKey)
    .digest('hex');

  return {
    assessmentId,
    assessmentKey,
    claimId: dto.claimId,
    userId: dto.userId,
    campaignId: dto.campaignId,
    evaluationVersion: dto.evaluationVersion,
    score: 0,
    level: 'LOW',
    decision: 'ALLOW',
    groupScores: { D: 0, N: 0, I: 0, V: 0 },
    reasons: [],
    ruleVersion: 'stub-v1',
    evaluatedAt: new Date().toISOString(),
  };
}

Internal token guard

src/risk/internal-token.guard.tsTypeScript
canActivate(context: ExecutionContext): boolean {
  const request = context.switchToHttp().getRequest<Request>();
  const token = request.headers['x-internal-token'];
  const expected = process.env.INTERNAL_SERVICE_TOKEN;

  if (!expected || token !== expected) {
    throw new UnauthorizedException({
      code: 'INVALID_INTERNAL_TOKEN',
      message: 'Internal token không hợp lệ',
    });
  }

  return true;
}

Token sai hoặc thiếu đều trả 401. Gateway bên ngoài đã chặn /internal/, nên đây là lớp bảo vệ thứ hai.

Tình huốngS1 làm gìClient thấy

Claim PENDING sau lỗi sẽ nằm chờ. Schema đã có nextRetryAt, retryCount, maxAttempts. Worker quét claim PENDING và gọi lại S2 sẽ làm ở bước sau.

Hỏi đáp

Câu hỏi có thể bị hỏi

Vì sao S2 trả ALLOW mà claim chưa ACTIVE?

Vì bước 3b chỉ lưu kết quả. Việc áp policy (ALLOW → ACTIVE, VERIFY → VERIFY_REQUIRED, REJECT → REJECTED) là bước 3c. Tách như vậy để test từng phần: gọi S2 đúng trước, rồi mới xử lý trạng thái.

assessmentId được tạo thế nào?

SHA256(claimId:evaluationVersion). Cùng claim và cùng version luôn cho cùng ID, nên S2 idempotent mà chưa cần database. Khi S2 có Neo4j, ID này có thể dùng làm khóa duy nhất.

Vì sao S1 không gửi fingerprint sang S2 ở bước này?

Vì S1 chưa thu thập fingerprint/IP. Hợp đồng API đã có chỗ để mở rộng; khi làm S2 thật sẽ thêm trường tín hiệu. Hiện tại chỉ cần đủ để nối luồng.

Nếu S2 trả decision lạ thì sao?

Bước 3c sẽ validate decision thuộc ALLOW | VERIFY | REJECT. Nếu lạ, coi như lỗi và giữ PENDING, không tự suy diễn.

Vì sao dùng internal token thay vì JWT?

JWT đại diện cho người dùng. Gọi service-to-service không có người dùng cụ thể, nên dùng token tĩnh chia sẻ giữa service. Đơn giản hơn và không cần phát token cho máy.

Có cần gọi S2 lại khi client retry không?

Nếu claim đã có assessmentId, không gọi lại. Nếu lần trước S2 lỗi (assessmentId null), retry sẽ gọi lại. Điều này tránh đánh giá trùng và vẫn phục hồi được sau lỗi.

Tiếp theo

Bước 3c — Áp auto policy

ALLOW → ACTIVE, đặt activatedAt, expiresAt, phát outbox trial.activated.v1.

VERIFY → VERIFY_REQUIRED, tạo OTP (TTL 10 phút), outbox audit.

REJECT → REJECTED, phát outbox trial.rejected.v1.

Kèm kiểm tra evaluationVersion và version để bỏ qua kết quả cũ.
