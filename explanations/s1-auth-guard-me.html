JwtAuthGuard & /api/users/me

Guard đọc Authorization: Bearer <token>, kiểm tra chữ ký và hạn dùng, rồi gắn user vào request. Route /me trả hồ sơ của chính người đang đăng nhập.

200 có token 401 thiếu token 401 token sai CanActivate @UseGuards

# Tóm tắt

Điều gì đã thay đổi và vì sao.

Đã xong

Thêm JwtAuthGuard để chặn request không có token hợp lệ. Thêm GET /api/users/me trả userId, email, role, status, emailVerified, createdAt. Không trả passwordHash.

Chưa làm

Chưa có role guard cho ADMIN, chưa thu hồi token, chưa kiểm tra tài khoản bị khóa trong guard. Những phần đó để bước sau.

# Request đi qua guard thế nào?

Guard chạy trước khi vào controller.

1
Clienthôm nay

Gửi GET /api/users/me kèm header Authorization: Bearer eyJ....

2
JwtAuthGuardhôm nay

Tách header thành hai phần: scheme Bearer và token. Nếu thiếu hoặc sai scheme → 401 AUTH_TOKEN_MISSING.

3
JwtService.verifyAsynchôm nay

Kiểm tra chữ ký bằng JWT_SECRET và thời hạn exp. Sai chữ ký hoặc hết hạn → 401 AUTH_TOKEN_INVALID.

4
Guard cho đi tiếphôm nay

Gắn payload vào request.user, trả true. Nest mới gọi vào controller.

5
UsersController + UsersServicehôm nay

@CurrentUser() lấy payload, dùng sub (userId) query DB và trả hồ sơ đã lọc.

Luồng ngắntext
Authorization: Bearer <token>
        │
        ▼
JwtAuthGuard.canActivate()
        │  thiếu / sai định dạng → 401 AUTH_TOKEN_MISSING
        ▼
JwtService.verifyAsync(token)
        │  sai chữ ký / hết hạn → 401 AUTH_TOKEN_INVALID
        ▼
request.user = { sub, role, iat, exp }
        │
        ▼
@CurrentUser() → user.sub
        │
        ▼
UsersService.getProfile(userId)
        │
        ▼
200 { userId, email, role, status, emailVerified, createdAt }

# Guard hoạt động thế nào?

src/auth/jwt-auth.guard.tsTypeScript
@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private readonly jwtService: JwtService) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest<AuthenticatedRequest>();
    const token = this.extractToken(request);

    if (!token) {
      throw new UnauthorizedException({
        code: 'AUTH_TOKEN_MISSING',
        message: 'Thiếu access token',
      });
    }

    try {
      // verifyAsync kiểm tra cả chữ ký lẫn thời hạn (exp).
      const payload = await this.jwtService.verifyAsync<JwtPayload>(token);
      request.user = payload;
      return true;
    } catch {
      throw new UnauthorizedException({
        code: 'AUTH_TOKEN_INVALID',
        message: 'Access token không hợp lệ hoặc đã hết hạn',
      });
    }
  }

  private extractToken(request: AuthenticatedRequest): string | undefined {
    const [type, token] = request.headers.authorization?.split(' ') ?? [];
    return type === 'Bearer' ? token : undefined;
  }
}

CanActivate là gì?

Là interface của Nest cho guard. Guard chạy trước controller để trả lời câu hỏi: “request này có được đi tiếp không?”.

  • return true → cho đi tiếp.
  • return false → Nest trả 403.
  • throw UnauthorizedException → Nest trả 401 với body mình chọn.
Vì sao dùng throw thay vì return false?

Trả 401 kèm { code, message } rõ ràng hơn 403 mặc định. Client biết chính xác thiếu token hay token sai.

Vì sao không dùng passport?

Passport phù hợp khi có nhiều chiến lược đăng nhập (Google, Facebook, API key...). Ở đây chỉ có một loại Bearer JWT, nên tự viết guard giúp ít dependency hơn và dễ hiểu luồng. Nếu sau này thêm OAuth, có thể chuyển sang @nestjs/passport.

# Decorator CurrentUser

src/auth/current-user.decorator.tsTypeScript
export const CurrentUser = createParamDecorator(
  (_data: unknown, context: ExecutionContext): JwtPayload => {
    const request = context
      .switchToHttp()
      .getRequest<{ user: JwtPayload }>();

    return request.user;
  },
);

Nếu không có decorator, controller phải viết @Req() req rồi req.user.sub. Decorator gom phần lặp đó lại, và che đi kiểu Request của Express.

src/users/users.controller.tsTypeScript
@Controller('api/users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get('me')
  @UseGuards(JwtAuthGuard)
  getMe(@CurrentUser() user: JwtPayload): Promise<UserProfile> {
    return this.usersService.getProfile(user.sub);
  }
}
Thứ tự chạy

JwtAuthGuard → @CurrentUser() → service. Nếu guard ném 401, controller không được gọi, nên user luôn tồn tại khi vào handler.

# Service trả hồ sơ

src/users/users.service.tsTypeScript
async getProfile(userId: string): Promise<UserProfile> {
  const account = await this.prisma.account.findUnique({
    where: { userId },
    select: {
      userId: true,
      emailNormalized: true,
      role: true,
      status: true,
      emailVerified: true,
      createdAt: true,
    },
  });

  if (!account) {
    throw new NotFoundException({
      code: 'USER_NOT_FOUND',
      message: 'Không tìm thấy tài khoản',
    });
  }

  return {
    userId: account.userId,
    email: account.emailNormalized,
    role: account.role,
    status: account.status,
    emailVerified: account.emailVerified,
    createdAt: account.createdAt,
  };
}

Vì sao vẫn cần query DB?

Token chỉ chứa sub và role, không chứa email, trạng thái hay ngày tạo. Muốn trả hồ sơ đầy đủ thì phải đọc DB. Đây cũng là chỗ kiểm tra tài khoản còn tồn tại hay không.

Trường hợp token còn hạn nhưng user đã bị xóa

Guard vẫn cho qua vì chữ ký hợp lệ, nhưng service trả 404 USER_NOT_FOUND. Nếu muốn chặn sớm, có thể kiểm tra user trong guard — đổi lại mỗi request tốn thêm một query.

# Vì sao export JwtModule?

AuthModule đã cấu hình JwtModule với JWT_SECRET. UsersModule cần JwtService cho guard, nhưng không nên cấu hình JWT lần hai — dễ lệch secret hoặc lặp code.

src/auth/auth.module.tsTypeScript
@Module({
  imports: [JwtModule.registerAsync({ ... })],
  controllers: [AuthController],
  providers: [AuthService, JwtAuthGuard],
  // Cho UsersModule dùng lại JwtService và guard
  exports: [JwtModule, JwtAuthGuard],
})

UsersModule chỉ cần imports: [AuthModule]. Đây là cách Nest chia sẻ dependency giữa các module mà không tạo thêm instance.

# Câu hỏi có thể bị hỏi

Guard chạy trước hay sau ValidationPipe?

Guard chạy trước pipe, interceptor và handler. Nếu token sai, request bị chặn ngay, không tốn công validate body hay query DB.

Vì sao 401 mà không phải 403?

401 = chưa xác thực (thiếu hoặc sai token). 403 = đã xác thực nhưng không có quyền. Ví dụ user thường gọi route ADMIN sẽ là 403.

Token hợp lệ nhưng tài khoản bị khóa thì sao?

Hiện guard chưa kiểm tra status, nên vẫn cho qua; service trả hồ sơ với status hiện tại. Muốn chặn ngay, thêm query kiểm tra status === 'ACTIVE' trong guard — đổi lại mỗi request tốn thêm một query.

Tại sao không gửi token qua query string?

Query string dễ bị ghi vào log, lịch sử trình duyệt và referer. Header Authorization không bị những vấn đề đó, và là chuẩn cho Bearer token.

Token bị lộ thì sao?

Kẻ tấn công dùng được đến khi token hết hạn (tối đa 1 giờ). Vì JWT stateless, muốn thu hồi ngay cần thêm blacklist hoặc đổi secret (làm mất hiệu lực toàn bộ token). Với MVP, hạn 1 giờ là mức giảm thiệt hại chấp nhận được.

Vì sao response không có passwordHash?

Nguyên tắc tối thiểu dữ liệu. Dù hash khó đảo ngược, client không cần nó. Không trả ra ngoài thì không có nguy cơ rò rỉ qua log, cache hay DevTools.
