AuthModule · Register

Đăng ký tài khoản,
hiểu từng bước.

Một request đăng ký đi qua validation, chuẩn hóa email, hash mật khẩu và PostgreSQL. Tài liệu này giải thích vì sao mỗi bước tồn tại.

Tóm tắt nhanh

  • Thêm endpoint POST /api/auth/register cho S1.
  • Email được chuẩn hóa (trim + lowercase) trước khi lưu để tránh trùng tài khoản.
  • Mật khẩu được hash bằng bcrypt (12 rounds); DB không bao giờ thấy mật khẩu gốc.
  • Trùng email trả 409 EMAIL_ALREADY_EXISTS, dữ liệu sai trả 400 VALIDATION_ERROR.
  • Đã test thành công qua gateway http://localhost:8080 và kiểm tra trực tiếp trong PostgreSQL.

Một request đi qua đâu?

Đây là toàn bộ đường đi của lệnh đăng ký. Mỗi ô là một lớp có nhiệm vụ riêng.

1 Client gửi JSON email + password
→
2 NGINX :8080 route /api/auth/* vào S1
→
3 ValidationPipe kiểm tra định dạng DTO
→
4 AuthService chuẩn hóa + hash mật khẩu
→
5 PostgreSQL INSERT vào bảng accounts

Vì sao validation đứng trước service? Dữ liệu sai bị chặn ngay cửa, không tốn CPU để hash mật khẩu và không tạo request rác vào database.

Bước 1 — Chặn dữ liệu sai bằng DTO

DTO (Data Transfer Object) là bản mô tả “body hợp lệ trông như thế nào”. ValidationPipe đọc các decorator để kiểm tra.

src/auth/dto/register.dto.tsimport { IsEmail, IsString, MaxLength, MinLength } from 'class-validator'; export class RegisterDto { @IsEmail({}, { message: 'Email không hợp lệ' }) @MaxLength(254, { message: 'Email quá dài' }) email!: string; @IsString({ message: 'Mật khẩu phải là chuỗi' }) @MinLength(8, { message: 'Mật khẩu phải có ít nhất 8 ký tự' }) @MaxLength(72, { message: 'Mật khẩu không được quá 72 ký tự' }) password!: string; }

Vì sao giới hạn 72 ký tự?

bcrypt chỉ xử lý tối đa 72 byte đầu vào. Ký tự tiếng Việt có thể chiếm nhiều byte, nên giới hạn ở mức ký tự giúp tránh trường hợp người dùng tưởng mật khẩu dài nhưng phần sau bị bỏ qua.

Lưu ý: giới hạn 72 ký tự là chặn ở mức ký tự, chưa quy đổi sang byte. Với mật khẩu thuần ASCII thì hoàn toàn chính xác; nếu cần chặt hơn, có thể kiểm tra Buffer.byteLength() trong service.

Bước 2 — Controller chỉ làm một việc

Controller nhận request và chuyển cho service. Không hash, không query DB — nhờ vậy dễ test và dễ đọc.

src/auth/auth.controller.ts@Controller('api/auth') export class AuthController { constructor(private readonly authService: AuthService) {} @Post('register') @HttpCode(HttpStatus.CREATED) register(@Body() dto: RegisterDto): Promise<RegisterResult> { return this.authService.register(dto); } }

Vì sao đường dẫn là api/auth?

NGINX đang chuyển nguyên path /api/auth/register vào service mà không cắt tiền tố. Vì vậy controller phải khai báo đầy đủ api/auth để khớp cấu hình hiện tại.

Bước 3 — Service: chuẩn hóa, hash, lưu

Đây là nơi chứa toàn bộ logic nghiệp vụ. Ba việc quan trọng nhất được giải thích ngay bên dưới.

src/auth/auth.service.ts (rút gọn)async register(dto: RegisterDto): Promise<RegisterResult> { // 1. Chuẩn hóa email const emailNormalized = dto.email.trim().toLowerCase(); const emailDomainKey = emailNormalized.split('@')[1] ?? ''; // 2. Hash mật khẩu const passwordHash = await hash(dto.password, BCRYPT_ROUNDS); // 3. Ghi DB + bắt lỗi trùng unique try { const account = await this.prisma.account.create({ ... }); return { userId: account.userId, email: account.emailNormalized, ... }; } catch (error) { if (error instanceof Prisma.PrismaClientKnownRequestError && error.code === 'P2002') { throw new ConflictException({ code: 'EMAIL_ALREADY_EXISTS', message: 'Email đã được đăng ký', }); } throw error; } }

Vì sao chuẩn hóa email?

Người dùng rất hay gõ Alice@Example.com và alice@example.com. Nếu lưu nguyên, hệ thống tạo hai tài khoản cho cùng một người — vừa sai nghiệp vụ, vừa mở đường cho gian lận multi-account. Chuẩn hóa về lowercase + trim biến hai chuỗi trên thành một.

Vì sao lưu thêm email_domain_key?

Đây là dấu vân tay domain, ví dụ example.com. S2 (Graph & Risk) dùng nó để phát hiện một loạt tài khoản cùng domain đăng ký trong thời gian ngắn — một tín hiệu gian lận phổ biến. Nếu chỉ lưu email đầy đủ, mỗi lần phát hiện phải cắt chuỗi; lưu sẵn giúp truy vấn nhanh và rõ nghĩa.

Vì sao hash mật khẩu?

Hash là hàm một chiều: từ mật khẩu tính ra chuỗi $2b$12$..., nhưng từ chuỗi đó gần như không thể suy ngược lại mật khẩu. Nếu database bị lộ, kẻ tấn công chỉ thấy hash. bcrypt còn cố tình chậm (12 rounds ≈ 250–400ms mỗi lần) để việc dò hàng tỷ mật khẩu trở nên quá đắt.

Vì sao bắt lỗi P2002 thay vì kiểm tra trước?

Có thể viết “tìm email → nếu chưa có thì tạo”. Nhưng hai request cùng email chạy song song có thể cùng lọt qua bước tìm. Database mới là nơi phân xử cuối cùng nhờ ràng buộc UNIQUE. Bắt lỗi P2002 (unique constraint) vừa chính xác vừa tránh thêm một vòng query.

Nguyên tắc: kiểm tra ở tầng ứng dụng để báo lỗi đẹp, nhưng luôn để database làm chốt chặn cuối.

Bước 4 — Bật ValidationPipe toàn cục

Một dòng cấu hình trong main.ts khiến mọi DTO trong service được kiểm tra tự động.

src/main.tsapp.useGlobalPipes( new ValidationPipe({ whitelist: true, transform: true, exceptionFactory: (errors) => new BadRequestException({ code: 'VALIDATION_ERROR', message: 'Dữ liệu không hợp lệ', details: errors.map((error) => ({ field: error.property, errors: Object.values(error.constraints ?? {}), })), }), }), );

whitelist: true

Field lạ không khai báo trong DTO bị loại bỏ. Tránh việc client gửi thêm role: "ADMIN".

transform: true

Tự chuyển body JSON thành instance của DTO để decorator hoạt động đúng kiểu.

exceptionFactory

Đổi lỗi mặc định thành cùng format { code, message, details } với lỗi nghiệp vụ.

Kết quả thực tế

Đã chạy qua gateway và kiểm tra dữ liệu trong PostgreSQL.

1. Đăng ký thành công — 201

POST /api/auth/register{ "email": "Alice@Example.com", "password": "mat-khau-123" } → 201 Created { "userId": "3d829d22-ccf2-45a7-b8f7-45af44f26b63", "email": "alice@example.com", "role": "USER", "createdAt": "2026-11-06T08:21:41.371Z" }

2. Đăng ký trùng email — 409

{ "code": "EMAIL_ALREADY_EXISTS", "message": "Email đã được đăng ký" }

3. Dữ liệu sai — 400

{ "code": "VALIDATION_ERROR", "message": "Dữ liệu không hợp lệ", "details": [ { "field": "email", "errors": ["Email không hợp lệ"] }, { "field": "password", "errors": ["Mật khẩu phải có ít nhất 8 ký tự"] } ] }

4. Kiểm tra trong database

SELECT email_normalized, email_domain_key, left(password_hash, 7), role FROM accounts; alice@example.com | example.com | $2b$12$ | USER

Chuỗi $2b$12$ cho biết: bcrypt phiên bản 2b, độ khó 12 rounds. Mật khẩu gốc không xuất hiện ở bất kỳ đâu.

Vì sao chọn bcryptjs?

bcrypt (native)

  • Nhanh hơn
  • Cần biên dịch C++ khi cài
  • Dễ lỗi trong Docker slim nếu thiếu build tools

bcryptjs (đang dùng)

  • Thuần JavaScript, cài là chạy
  • Không cần compiler trong image
  • Chậm hơn một chút — không đáng kể với đăng ký

Với đồ án 8 tuần, ưu tiên chạy ổn định trên mọi máy quan trọng hơn vài mili-giây. Nếu sau này cần tối ưu, có thể đổi sang argon2 hoặc bcrypt native mà không đổi logic nghiệp vụ.

Ghi chú thiết kế: bản thiết kế trước ghi Argon2id. Nhóm đã chốt dùng bcrypt 12 rounds cho MVP vì bcryptjs không cần biên dịch native trong Docker. Đánh đổi: Argon2id kháng GPU/ASIC tốt hơn; có thể chuyển sau mà không đổi schema hay API.

Những gì chưa làm

  • Đăng nhập + JWT: hiện chỉ có đăng ký, chưa phát token.
  • Xác thực email: cột email_verified đang mặc định false, chưa có luồng gửi OTP.
  • Rate limit: chưa chặn spam đăng ký; có thể thêm ở gateway hoặc service sau.
  • Kiểm tra độ mạnh mật khẩu: hiện chỉ yêu cầu 8 ký tự, chưa bắt buộc chữ hoa/số.

Đây là chủ ý để giữ bước nhỏ, chạy được trước rồi mở rộng.

Câu hỏi có thể bị hỏi khi bảo vệ

Vì sao không lưu mật khẩu trực tiếp?

Vì database có thể bị lộ hoặc bị admin xem. Hash một chiều đảm bảo lộ DB không đồng nghĩa lộ mật khẩu. bcrypt còn thêm salt tự động, nên hai người cùng mật khẩu vẫn có hash khác nhau.

Vì sao dùng 12 rounds mà không phải 4 hay 20?

4 rounds quá nhanh, dễ bị brute-force. 20 rounds quá chậm, làm đăng ký/đăng nhập chờ lâu. 12 là mức cân bằng phổ biến hiện nay, mỗi lần hash mất khoảng 250–400ms trên máy dev.

Nếu hai người đăng ký cùng email cùng lúc thì sao?

Một request sẽ thắng và tạo tài khoản. Request còn lại bị PostgreSQL chặn bởi ràng buộc UNIQUE(email_normalized), Prisma trả mã P2002, service đổi thành HTTP 409. Không có tài khoản trùng.

Vì sao response không trả passwordHash?

Nguyên tắc tối thiểu dữ liệu: client không cần hash để làm gì. Trả về chỉ làm tăng nguy cơ rò rỉ qua log, cache hoặc DevTools.

Email có dấu tiếng Việt thì sao?

toLowerCase() xử lý được chữ có dấu. Tuy nhiên chuẩn email quốc tế (EAI) phức tạp hơn; với phạm vi đồ án, chuẩn hóa trim + lowercase là đủ và nhất quán.
